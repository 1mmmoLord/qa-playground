#Виды тестирования

**По объекту и целям**

- Функциональное тестирование: Проверка того, что система делает то, что должна (работают ли кнопки, авторизация, логика расчетов). Сюда входят модульное (Unit), интеграционное, системное и приемочное тестирование.
- Нефункциональное тестирование: Оценка характеристик «Как работает система» (производительность, удобство, безопасность).

**По уровню изоляции (модели тестирования)**

- Модульное (Unit) тестирование: Проверка отдельных функций или классов в коде изолированно.
- Интеграционное тестирование: Проверка взаимодействия между несколькими модулями или внешними системами.
- Системное тестирование: Проверка всей системы целиком на соответствие требованиям.
- Приемочное тестирование (UAT): Проверка готовности продукта со стороны заказчика или реальных пользователей перед выпуском.

**По знанию внутренней структуры**

- Черный ящик (Black-box): Тестировщик не видит код и проверяет систему только через интерфейс.
- Белый ящик (White-box): Тестировщик знает устройство программы и анализирует сам исходный код.
- Серый ящик (Gray-box): Промежуточный вариант (есть доступ к базе данных или логике на уровне API, но без полного разбора кода).

**По характеру сценариев**

- Позитивное тестирование: Проверка работы системы на корректных (ожидаемых) данных.
- Негативное тестирование: Проверка реакции программы на некорректные данные или действия (например, ввод текста вместо числа).

**Связанное с изменениями**

- Дымовое (Smoke) тестирование: Быстрая базовая проверка работоспособности сборки после изменений.
- Регрессионное тестирование: Проверка того, что новые правки не сломали старый функционал.

#Тест-дизайн

**Техники**

- Эквивалентное разделение (Equivalence Partitioning): входные данные делят на группы (классы эквивалентности), из каждой берут по одному типичному значению для проверки.
- Анализ граничных значений (Boundary Value Analysis): проверяются самые крайние значения и границы классов (например, минимум, максимум, чуть меньше и чуть больше нормы).
- Попарное тестирование (Pairwise): комбинируют пары параметров друг с другом, чтобы сократить число проверок без потери качества.
- Таблицы принятия решений (Decision Tables): строят матрицу условий и вариантов ответа системы для сложных логических связей.
- Предугадывание ошибок (Error Guessing): тесты создаются на основе опыта тестировщика и интуиции о том, где разработчик мог совершить ошибку.
- Диаграммы переходов состояний (State Transition): описывают поведение системы при переходе из одного состояния в другое.

**Результат тест-дизайна**

- Чек-листы (список проверок без жестких шагов).
- Тест-кейсы (подробный сценарий с предусловиями, шагами и ожидаемым результатом).

## Decision Table Testing

**Decision Table Testing** — техника тест-дизайна, при которой тест-кейсы строятся на основе комбинаций условий и соответствующих им действий системы.

**Когда применяется:**
- когда результат зависит от нескольких условий;
- когда бизнес-правила содержат комбинации «И» / «ИЛИ»;
- когда необходимо проверить все значимые сочетания условий.

**Основные элементы таблицы:**
- Условия (Conditions) — факторы, влияющие на результат.
- Правила (Rules) — комбинации значений условий.
- Действия (Actions) — ожидаемое поведение системы для каждой комбинации.

**Количество комбинаций:**

- N = 2ⁿ, где n — количество бинарных условий.

**Преимущество:** помогает находить пропущенные комбинации условий и систематизировать тестирование бизнес-логики.

**Ограничение:** при большом количестве условий количество комбинаций быстро увеличивается.
